# 👾 CWE-1254 — Incorrect Comparison Logic Granularity

> **The right answer, a talkative method.** The comparison is not done in a single
> operation but step by step. When a step fails to match, the operation ends right
> there. The answer is right — but **how long it took** says more than the answer
> itself.

## What Granularity Means

There are two ways to compare two things:

```
ATOMIC      look at all of it at once, give a single answer
GRANULAR    split it into pieces, look at them in order, stop at the first mismatch
```

Both give **the same right answer**: equal or not. The difference is in the way
the answer is reached.

The granular method looks faster and is fine for most jobs. If you have seen that
the first two bytes of a file differ, there is no point reading the remaining
gigabyte.

But if what you are comparing is **secret**, stopping early says something.

---

## The Price of Exiting Early

Think of a simple loop that compares a password:

```c
for (int i = 0; i < n; i++)
    if (girilen[i] != dogru[i])
        return YANLIS;      /* exit at the first difference */
return DOGRU;
```

The code works correctly. It says `YANLIS` (wrong) to a wrong password and
`DOGRU` (right) to the right one. It looks as if it leaks nothing — because **the
value it returns** leaks nothing.

What leaks is how many laps the loop ran:

```
input:  x???      first letter did not match   →  1 lap   →  the shortest time
input:  a???      one letter matched           →  2 laps  →  a little longer
input:  ab??      two letters matched          →  3 laps  →  longer
input:  abc?      three letters matched        →  4 laps  →  longer still
```

Every right letter delays the answer by a measurable amount. The answer is always
"wrong" — but **how wrong it is** can be read from the time.

> 🔑 This turns guessing the password from a combinatorial problem into a problem
> you work through **letter by letter**. The difference between them is the
> difference between exponential and linear.

The same pattern holds not only for passwords but for **every comparison of a
secret value**: message authentication codes (MACs), signature checks, session
keys, API tokens, answers to security questions.

---

## Why This Page Has Two Parents

In MITRE, 1254 has **two** parents, and that is a first in your catalogue:

```
CWE-697  Incorrect Comparison          →  the comparison was done in the wrong MANNER
CWE-208  Observable Timing Discrepancy →  the time difference is OBSERVABLE from outside
```

Both are right, because the weakness stands exactly at the crossroads. One side
looks at the question *"how did you build the comparison"*, the other at *"can
this difference be measured from outside"*.

Granularity on its own is not a weakness — it is perfectly sensible when
comparing files. A time difference on its own is not a weakness either. It
becomes a weakness **when the two meet on a secret value**.

## In NandGame You Built Its Opposite

Look at the comparison circuit you built in
[lesson 15](../salterden_bilgisayara/15_condition.md):

```
X (16 bits)  ──►  is zero  ──►  a 1-bit answer
```

`is zero` looks at all sixteen bits **at once**. There is no step in the circuit
like "the first three bits matched, move on to the next": every bit arrives on its
own wire, none waits for another. There is no loop counting matched bits, and no
path that stops at the first difference.

```
granular software:  how many steps it took tells how many pieces matched
atomic circuit:     there are no steps — and no early exit
```

> 📌 This does not mean the answer arrives in exactly the same time for every input.
> In [10](../salterden_bilgisayara/10_bayraklar.md#tree-or-chain) you saw that `is zero`
> can also be built as a chain: in a chain, the closer the 1 bit is to the start, the
> later the answer arrives. A tree shrinks the difference, but gate delays are never
> exactly equal. In the subtractor in front of `is zero`, the carry also settles in a
> time that depends on the numbers ([07](../salterden_bilgisayara/07_multibit_adder.md)).
> What makes everyone outside see the same time is not the circuit itself but the
> clock ([18](../salterden_bilgisayara/18_data_flip_flop.md)): whenever the result
> settles, it is read at the next bell.

> 🔑 A comparison circuit has no "stop at the first difference" path. In software,
> the default behaviour is exiting early. The weakness is born from choosing the fast
> option becoming a habit.

### And the fix is the same circuit

The standard software form of a constant-time comparison is this:

```c
unsigned char fark = 0;
for (int i = 0; i < n; i++)
    fark |= girilen[i] ^ dogru[i];   /* NO early exit */
return fark == 0;
```

Notice: this is exactly the separate equality circuit mentioned in
[10](../salterden_bilgisayara/10_bayraklar.md). Compare the bits with `xor`, accumulate
the differences, check whether any 1 is left. The last step, `is zero`, you built in
10 and used in 15.

| in the circuit | in the code |
|---|---|
| `xor` — are the two bits different | `girilen[i] ^ dogru[i]` |
| accumulate all the differences | `fark \|=` |
| `is zero` — is there any 1 in the result | `fark == 0` |

The loop always runs `n` laps. Nothing ends early. The number of laps does not
depend on the input.

So the `xor`s together with `is zero` are the **hardware original** of a safe
comparison. Software is trying to imitate it.

---

## Where You Meet It

| area | what is compared |
|---|---|
| Authentication | password, PIN, recovery code |
| Cryptography | MAC, signature, tag verification |
| Session management | token, cookie value, API key |
| Hardware | debug unlock key, secure boot signature |

The last row is why MITRE put this CWE in the **hardware** category: the same
mistake can be made in silicon too. A circuit that compares an unlock key piece
by piece leaks the same information as the loop in software.

---

## How to Prevent It

- **Do not exit early on a secret value.** The comparison should always take the
  same number of steps regardless of the input. The `xor` + accumulate pattern
  above is the standard fix.
- **Use a ready-made function.** Most languages have a constant-time comparator
  (`crypto.timingSafeEqual`, `hmac.compare_digest`, `CRYPTO_memcmp`). Call it
  instead of writing your own — the compiler may "optimise" yours into an early
  exit.
- **Do not trust the compiler, measure.** It is not enough for the code to look
  constant-time; the machine code produced has to be too. There are tools that
  measure this (`dudect`, `ctgrind`); in critical code it is measured, not
  assumed.
- **Compare first, branch afterwards.** Code that does a different amount of work
  depending on the result of the comparison leaks the time anyway. The difference
  should be collected into a single bit and checked once at the end.
- **The same rule in hardware.** A circuit comparing a key should evaluate all
  bits in parallel; a state machine that advances step by step produces the same
  leak.
- **List what is secret.** This weakness only applies to secret values. If you
  do not know which comparisons work on secret data, you cannot know which ones
  must be constant-time either.

## Summary — Keep in Mind

```
☐ CWE-1254: the comparison is done piece by piece and stops at the first mismatch.
☐ The answer is RIGHT. What leaks is not the answer but HOW LONG the answer took.
☐ Every right letter makes the loop one lap longer → "how wrong" can be read from the time.
☐ 🔑 It turns the guessing problem from exponential into LINEAR. That is the real danger.
☐ Not only for passwords: MAC, signature, token, API key, hardware unlock key.
☐ IT HAS TWO PARENTS: 697 (the manner of comparison) and 208 (the time difference is observable). It stands at the crossroads.
☐ Granularity on its own is not a weakness (sensible when comparing files). Neither is a time difference on its own.
☐ It becomes a weakness when the two meet on a SECRET VALUE.
☐ The circuit you built in lesson 15 is its OPPOSITE: is zero looks at 16 bits at once, no intermediate state.
☐ 🔑 A comparison circuit has no early-exit path; in software the default is exiting early. The weakness is born from habit.
☐ A circuit does not answer in exactly the same time for every input either (chain, carry). The clock shows the outside the same time.
☐ The fix pattern is the same as the circuit: fark |= a[i] ^ b[i] (no early exit), and fark == 0 at the end.
☐ The mapping: xor = are they different · |= = accumulate the differences · == 0 = is zero. You built is zero in 10; the xor equality circuit was mentioned in 10.
☐ Use a ready-made function: timingSafeEqual · compare_digest · CRYPTO_memcmp.
☐ ⚠️ The compiler can turn your constant-time code into an early exit — MEASURE (dudect, ctgrind), do not assume.
☐ A branch that does a different amount of work after the comparison leaks the time too: collect the difference, look once at the end.
```
