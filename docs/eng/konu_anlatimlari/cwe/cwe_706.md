# 👾 CWE-706 — Use of Incorrectly-Resolved Name or Reference

> **A name is not an identity.** A program uses a name or a reference to reach a
> resource. But at the moment it is used, that name resolves to **something
> else** — and where it arrives is outside the intended area.

| | |
|---|---|
| **Official name** | Use of Incorrectly-Resolved Name or Reference |
| **Abstraction level** | *Class* |
| **Parent** | CWE-664 — Improper Control of a Resource Through its Lifetime |
| **Its child in the catalogue** | [59](./cwe_59.md) — Link Following |

---

## The Gap Between the Name and the Thing

When you access a file as `/tmp/veri`, there are two separate things:

```
  the NAME you wrote       →  "/tmp/veri"
  the THING you reach      →  the real inode on disk
```

The translation between them is called **resolution**, and you do not do it —
the operating system does, **after** you wrote it, at the moment you use it.

> 🔑 The weakness lives exactly in this gap: **you choose the name, someone else
> does the resolution.** Anyone who knows the rules in between can make the same
> name resolve to something different.

You saw the concrete form of this in
[Leviathan's lesson 5](../leviathan_komutlari/what_leviathan_teaches.md#lesson-5--symbolic-link-attack--insecure-tmp):
the file's name stayed the same, the place it pointed to changed.

---

## Roads from the Same Root

What MITRE lists under this class shows how many different forms "the name
resolved to something else" can take:

| CWE | How it resolves |
|---|---|
| [**59**](./cwe_59.md) — Link Following | The name is a **link**; the link points elsewhere ✓ *you have it* |
| **22** — Path Traversal | The name contains `../`; the path steps **outside** the allowed folder |
| **41** — Path Equivalence | Several spellings of the same file: `dosya`, `dosya/`, `./dosya`, `dosya ` |
| **178** — Case Sensitivity | `Dosya` and `dosya` — the same on one file system, separate on another |
| **66** — Virtual Resources | The name is not a real file but a device or a special resource |
| **98** — PHP Remote File Inclusion | The name resolves to a remote address and the code comes from there |
| **386** · **827** | A symbolic name to the wrong object · an unchecked document type definition |

> 💡 **22 (Path Traversal)** is the most frequently met item on this list and is
> covered in the repo's web security series — but it has not been mapped to a
> CWE yet. Knowing that it sits under the same umbrella lets you put the two into
> a single mental folder.

The sentence they all share: **the name that was checked and the thing that was
used are not the same.**

---

## Why Checking Is Not Enough

The natural reflex is: *"then I will check it before using it."*

That is not enough, and the reason is already written in your catalogue:

```
  check   →   [ in this gap the name can be bound to something else ]   →   use
                                      ↑
                          CWE-367 (TOCTOU) is exactly here
```

The binding between the name and the thing was right **at the moment of the
check**. At the moment of use it resolves to something else. The distinction
between [59](./cwe_59.md) and [367](./cwe_367.md) comes from exactly here, and
the place where the two meet has its own number: **CWE-363**.

> 🔑 The fix is not "checking more carefully". It is **letting go of the name and
> holding on to the thing itself** — open the file once, then always use that
> handle. A name that is not resolved again cannot be fooled again.

---

## Why It Has Its Own Page

You do not label a real vulnerability with 706; the class level is abstract, the
most concrete tier is chosen
([the hierarchy rule](./README.md#the-hierarchy-between-cwes)).

The reason it has a page is this: only **one** of 706's children is written in
your catalogue ([59](./cwe_59.md)), and read on its own that child looks like "a
symbolic link problem". Yet the same root also works with `../`, with a
difference in letter case, and with a trailing space.

Once you see the pattern, the defence changes too: instead of taking measures
against symbolic links, you start thinking **"never trust name resolution"**.

---

## How to Prevent It

- **Use the handle, not the name.** Open the resource once and then always work
  through that open handle. Resolving the name again is another chance to be
  fooled.
- **Normalise, then check.** Turn the path into its absolute, simplified form
  (like `realpath`) and do the check on that form. Checking the raw input and
  using the raw input invites 41 and 22.
- **List what is allowed, not what is forbidden.** A "none of these" list is
  always incomplete; there are more spellings than you can count.
- **Limit resolution.** Use options that turn off link following (like
  `O_NOFOLLOW`), avoid creating files in shared directories.
- **Do not work by name in a privileged operation.** Code running with privilege
  should not directly resolve a name the user supplied.

## Summary — Keep in Mind

```
☐ CWE-706 is a CLASS: the thing reached through a name turned out different from the intended thing.
☐ You choose the name, the operating system does the RESOLUTION — and at the moment you use it.
☐ The weakness lives in the GAP between the name and the thing.
☐ Its children are forms of the same root: 59 (link) · 22 (../) · 41 (equivalent spelling) · 178 (letter case).
☐ 22 Path Traversal is covered in the repo's web security series, it has not been mapped yet.
☐ "I will check before using it" is NOT ENOUGH — CWE-367 (TOCTOU) gets in between.
☐ 59 = no check at all · 367 = a check exists, the race was lost · 363 = both at once.
☐ The fix is not a more careful check: LET GO OF THE NAME, HOLD ON TO THE THING ITSELF (an open handle).
☐ Defence: use a handle · normalise, then check · an allow list · O_NOFOLLOW.
```
