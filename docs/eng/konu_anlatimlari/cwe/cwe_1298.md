# 👾 CWE-1298 — Hardware Logic Contains Race Conditions

> **Two paths leaving the same wire race each other.** A signal reaches a gate by
> two different paths: one short, the other one gate longer. When the source
> changes, the two paths do not report at the same moment, and in the short gap
> between them the gate produces a wrong value. If that moment concerns a lock, a
> permission or a state machine, a spike that lasts an instant turns into a
> security hole.

## One Source, Two Paths

MITRE describes how this weakness is born in a single sentence:

> *"A race condition in logic circuits typically occurs when a logic gate gets
> inputs from signals that have traversed different paths while originating from
> the same source."*

Two signals going into a gate come from the same source but arrive by different
paths. When the source changes, they reach the gate at different moments. MITRE
also names the result: an unwanted value for a short time, a **glitch** (a
spike), and that glitch can be *"temporary or permanent"*.

> 💡 The word *glitch* also appears in [CWE-1247](./cwe_1247.md). Same word,
> different thing: in 1247 an attacker applies the glitch from outside, here the
> circuit produces it on its own.

The selector latch in
[17](../salterden_bilgisayara/17_d_latch.md#why-not-select) is exactly this
structure:

```
        ┌─────────────────────────────► and(st, d) ────────────┐
  st ───┤                                                       ├── or ──► output
        └──► inv ──► inverse st ──► and(inverse st, output) ────┘
               (one gate late)
```

`st` splits in two. One path goes straight to the write valve, the other first
passes through the `inv` and then reaches the hold valve. When `st` falls, the
write valve closes at once, but the hold valve opens one gate later. For that
short moment nobody is holding the loop.

---

## A Temporary Spike, a Permanent Fault

The "temporary or permanent" distinction in MITRE's sentence is the most
important thing these two lessons brought out.

In a circuit without a loop, a spike is **temporary**. A wrong value shows for an
instant, then the circuit settles on the right one. If the next circuit happens to
look at exactly that moment it sees the wrong value; if not, it is as if nothing
happened.

In a circuit with a loop, a spike can be **permanent**. If the wrong value gets
into the loop, the loop starts holding it, because holding is the loop's job. That
is exactly what happened in the experiment in 17:

| where | what was seen |
|---|---|
| NandGame, black-box `select` | passed (the game seems to compute the box in a single step) |
| NandGame, `select` opened up into parts, canvas | when `st` fell the output dropped from 1 to 0; the bit was lost |
| NandGame, the same circuit, Check solution | *"The circuit did not reach a stable state."* |
| gate-level simulation, slow `inv` | the bit was lost |
| gate-level simulation, all gates equally fast | it oscillated |
| gate-level simulation, fast `inv` | no trouble |

The same circuit, three different outcomes depending on the delays. **What
decides which one you get is not the design but the speed of the gates.** And the
speed of the gates changes with temperature, voltage and manufacturing. A circuit
that works fine on the desk can lose the bit on another chip or at another
temperature.

> 🔑 Feedback can turn a spike that would last an instant in a loop-free circuit
> into a permanent fault. That is why races are more dangerous in memory
> circuits.

## MITRE's Example: The Same Selector

The first example MITRE gives for this weakness is a 2×1 selector built from
gates:

```verilog
// 2x1 Multiplexor using logic-gates
module glitchEx( input wire in0, in1, sel, output wire z );
  wire not_sel;
  wire and_out1, and_out2;
  assign not_sel = ~sel;
  assign and_out1 = not_sel & in0;
  assign and_out2 = sel & in1;
  // Buggy line of code:
  assign z = and_out1 | and_out2; // glitch in signal z
endmodule
```

You do not need to know the language; the lines are familiar: `not_sel` is the
inverse selection, the two `&`s are two valves, and `|` is the `or` joining them.
Put it next to the selector latch from 17:

| MITRE | the latch in 17 |
|---|---|
| `sel` | `st` |
| `in1` | `d` |
| `in0` | the output itself (feedback) |

The only difference is `in0`. In MITRE's selector `in0` comes from outside, and
the spike shows up on `z` for an instant and disappears. In the latch `in0` is
the output itself, so the spike gets into the loop and becomes permanent. These
two circuits are the two sides of the "temporary or permanent" distinction
above.

MITRE's fix is to add a single term:

```verilog
assign z <= and_out1 or and_out2 or (in0 and in1);
```

While `in0` and `in1` are both 1, this term holds `z` at 1 independently of
`sel`. The **Earle latch** term from 17, `and(d, output)`, is exactly this.

> ⚠️ MITRE's fix line is not valid Verilog as written: `assign` is not used with
> `<=`, and `or` / `and` are not operators inside an expression. iverilog gives a
> syntax error on this line. The valid form is:
>
> ```verilog
> assign z = and_out1 | and_out2 | (in0 & in1);
> ```
>
> Both versions were simulated with a delay of one unit on every assignment. With
> `in0 = in1 = 1`, when `sel` went from 1 to 0, `z` dropped to 0 for one step in
> the buggy code and did not drop in the fixed code.

## The Other Races in 16 and 17

The selector is not the only example. In these two lessons a race came up in
three places:

| where | source | two paths | result |
|---|---|---|---|
| [16 · leaving `0 0`](../salterden_bilgisayara/16_sr_latch.md#the-unused-row) | none, two separate inputs | `s` and `r` rise at the same moment | oscillation; the command of the one rising last wins; metastability if the gap is tiny |
| [17 · the instant spike](../salterden_bilgisayara/17_d_latch.md#a-spike-that-lasts-an-instant) | `d` | `d` directly, `inverse d` one gate late | for an instant `s = r = 0`; if `st` falls right then, oscillation |
| [17 · the selector latch](../salterden_bilgisayara/17_d_latch.md#why-not-select) | `st` | the write valve directly, the hold valve through the `inv` | a lost bit or oscillation |

The first row does not fit MITRE's definition exactly, because there the two
signals come not from the same source but from two separate inputs. But the
result belongs to the same family: what decides the outcome is not the design but
the order in which two signals arrive. The second and third rows are the
definition itself.

## Why It Is a Child of 362

The definition of [362](./cwe_362.md): concurrent access to a shared resource
without synchronisation set up. Here the shared resource is a **wire** (`st` or
`d`), and what accesses it concurrently are the two **paths** fed from that wire.
Nothing between them says "you first, then me".

MITRE's second example shows the kinship even more clearly. In a chip, a unit
that accesses memory directly checks the address and the permission setting
before allowing an access. But those two checked values can be changed from
outside while the operation is running. The attacker starts with a permitted
address and, while the operation is running, swaps it for an address that is not
permitted.

This is a race that slips in between a check and a use:
what you checked changed before you used it. MITRE's fix is familiar too: copy the
values into local registers at the start of the operation, and do both the check
and the use on that copy.

## How to Prevent It

MITRE recommends three things, and all three found a counterpart in these
lessons:

- **Protect with an extra term** (*logic redundancy*). *"Logic redundancy can be
  implemented along security critical paths to prevent race conditions."* Both
  the Earle latch's `and(d, output)` term and MITRE's `(in0 and in1)` term are
  this: redundant as logic, life-saving as timing.
- **See the race at design time.** MITRE mentions *Karnaugh maps*: a method that
  lays out a truth table so that rows differing in only one input sit next to each
  other. If two neighbouring rows give the same output but no term covers both of
  them together, that transition can produce a spike. That is how the missing term
  in the selector is found. (Not covered in this series yet.)
- **A secure default against metastability.** *"To avoid metastability, it is a
  good practice in general to default to a secure state in which access is not
  given to untrusted agents."* In the race in 16 the result could not be known in
  advance. A result that cannot be known should fall to the locked side.

Two more rules came out of these two lessons:

- **Follow the timing rule.** The spike in 17 only did harm if `st` fell while `d`
  was changing. Real chips write this rule down as a duration (*setup* and *hold
  time*). The clock exists to put all changes in an order that keeps to it.
- **Do not trust the black box; test at gate level.** The `select` box in
  NandGame passed, because the game seemed to compute it without delay, in a
  single step. The same logic failed once it was opened up into parts. A test
  built from ideal parts cannot see a race that is born from delays.
