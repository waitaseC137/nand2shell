# 👾 CWE-1271 — Uninitialized Value on Reset for Registers Holding Security Settings

> **The lock wakes up with a value nobody chose.** A security-related bit was not
> forced to a known value at power-on or on reset. Small physical differences in
> the circuit decide which value it starts with. On some boots, the door that
> should be closed starts **open**.

|---|---|

## There Are Stable States, but Nobody Chooses

The SR Latch's level description had this sentence:

> *"Until the first set or reset signal, the output is undefined."*

You saw the reason in
[lesson 16](../salterden_bilgisayara/16_sr_latch.md#count-the-inversions): the
two-`nand` loop confirms itself and rests comfortably at **both** values. Both are
equally stable.

When power first arrives, the two gates have to fall one way. Nobody chooses
which way. The choice is made by:

- Small differences in the lengths of the wires
- Tiny imbalances in the transistors left over from manufacturing
- Temperature

NandGame openly accepts this uncertainty: *"any output is allowed."* In the game
it is harmless. Once the bit being held is a **lock**, it stops being harmless.

---

## The Window

MITRE describes the problem as a **window of time**:

> *"When the device is first brought out of reset, the state of registers will be
> indeterminate if they have not been initialized by the logic. Before the
> registers are initialized, there will be a **window** during which the device is
> in an insecure state."*

```
power arrived / reset ended
        │
        ▼
  ┌─────────────────────────┐
  │  lock bit = unknown     │   ← THE WINDOW: insecure, because the value is random
  └─────────────────────────┘
        │
        ▼
  first write: lock = 1 (locked)
```

Note one thing in the diagram: what closes the window is **not** the first
write; the first write is the window's **end.** For the window never to open,
the value has to be forced while reset is active (below, in the fix).

The window may be short. But the sentence from [CWE-362](./cwe_362.md)'s page
holds here too: however narrow the window is, it is not zero.

---

## MITRE's Example: Resetting Over and Over

MITRE's example is a single bit that locks a test/debug interface (JTAG). The
code is in Verilog:

```verilog
always @(posedge clk) begin
  if (en) lock_jtag <= d;
end
```

Let us read it line by line:

```
always @(posedge clk)   →  every time the clock rises
if (en)                 →  if there is permission to "write"
lock_jtag <= d          →  write d into the lock bit
```

This is a **flip-flop**, a part you build two levels after the SR Latch. The
problem, however, is the same as in the SR Latch: **what is the value of
`lock_jtag` until "write" permission arrives?** The code never says.

MITRE describes the attack like this:

> *"In this example, an attacker can **reset the device until the test and debug
> interface is unlocked** and access the test interface until the lock signal is
> driven to a known state by the logic."*

The attacker resets the device over and over and waits to land on a boot where
the lock wakes up **open**. Every boot is a coin toss.

### How many tries until it works?

Let the probability that the lock wakes up open on each boot be `p`. If the boots
are independent of each other, the probability that it wakes up open **at least
once** in `n` tries is:

```
1 − (1 − p)ⁿ

p = 1/2,  n = 10   →  1 − (1/2)¹⁰  ≈  0.999
```

Ten resets, 99.9 percent. A reset is cheap and takes seconds.

In reality `p` is not 1/2 on every chip. Manufacturing differences favour one
side. That cuts both ways: some chips almost never wake up open, some almost
always do. You cannot know which one you have. That is why "it usually wakes up
locked" does not count as a guarantee.

### The fix

```verilog
always @(posedge clk) begin
  if (~reset) lock_jtag <= 0;
  else if (en) lock_jtag <= d;
end
```

The single added line: *"While reset is active, force the lock bit to a known
value."* The `~` in `~reset` means "not". The reset signal is **active low**:
as long as it is 0, reset is active (like `RESET#` in
[16](../salterden_bilgisayara/16_sr_latch.md#the-command-is-zero)). The value is
set inside the reset, without waiting for the first write, and the window never
opens.

> ⚠️ MITRE does not say whether the `0` in the code is **locked** or **open**:
> *"The flip-flop can be set to a known value (0 or 1) on reset."* On this page's
> diagram we said 1 = locked. Under that contract this line would have to be
> `lock_jtag <= 1`, because `0` starts the lock **open**. A known value is not
> enough; the known value has to be **the locked one** (see *fail-secure*
> below).

## Its Cousin in Software

In software its name is far more familiar: **CWE-457** — *Use of Uninitialized
Variable*. You read a variable that was never given a value, and you get whatever
was left in memory at that moment. MITRE put the two under the same family:

```
CWE-665  Improper Initialization
   ├─ CWE-909  Missing Initialization of Resource
   │     └─ CWE-1271   hardware: a security bit undefined on reset
   └─ CWE-908  Use of Uninitialized Resource
         └─ CWE-457    software: a variable never given an initial value
```

The difference between them is in the source. In software the "undefined" value
is usually something left over in memory, the leftovers of a previous job. In hardware it is **physics**: no design decision
chooses which of the two stable states it falls into; physics does. The line is
not sharp, though: when the machine first powers on, the memory software reads
is also full of values nobody has written yet, values physics chose.

---

## The Clock Doesn't Close It Either

In [18](../salterden_bilgisayara/18_data_flip_flop.md#undefined-at-power-on-again)
the clock arrived and made races invisible. But it did not touch the moment of
power-on. Inside the Data Flip-Flop there are two SR Latches, and both wake up in
a state nobody chose. The level's note says the same: *"output before the first
store and clock cycle is unspecified."*

When the flip-flop was simulated at gate level, some power-ons flickered **before
the first showing** (before the first fall after a store); after that there was
no problem in any step. But the flicker is not the real reason for the window;
the sentence above is: even when the SR Latches wake up without flickering,
nobody chooses which value they wake up in, so the output is still unknown. So
the clock does not close the window either; it ends at the first showing. The
solution stays the same: force the known value while reset is active.

---

## How to Prevent It

- **Force every security-related register to a known value on reset.** MITRE's
  advice: *"All registers holding security-critical information should be set to
  a specific value on reset."*
- **Make the known value the secure value.** The reset value of a lock bit should
  be **locked**. Opening should require a deliberate, authorised operation;
  closing should not. This is called *fail-secure*: if something goes wrong, the
  door stays closed.
- **Look for flip-flops without an initial value in the design.** MITRE: *"Design
  checks should be performed to identify any uninitialized flip-flops used for
  security-critical functions."* Design tools can do this automatically.
- **Do not try to measure the window, close it.** "The window is very short,
  nobody will land in it" is not a defence. If a reset is cheap, the attacker
  repeats the attempt.
- **If the only way out of an undefined state is a reset, the reset must be
  reliable.** [CWE-1245](./cwe_1245.md) and this page meet at this point: in 1245
  the way out of an undefined state is a reset, in 1271 the reset itself leaves an
  undefined state.

## Summary — Keep in Mind

```
☐ The SR Latch has two stable states and both are EQUALLY stable. Nobody chooses which one it falls into at power-on.
☐ Physics does the choosing: wire lengths, manufacturing imbalances, temperature.
☐ Harmless in NandGame ("any output is allowed"). Not harmless if the bit held is a LOCK.
☐ MITRE: there is a WINDOW between reset and the first write; the device is insecure in that window.
☐ However narrow the window is, it is not zero.
☐ MITRE's example: a JTAG lock bit with no reset value. The attack: RESET OVER AND OVER, wait for it to wake up open.
☐ The probability of landing it at least once in n tries is 1 − (1 − p)ⁿ. p = 1/2, n = 10 → 99.9%.
☐ p differs from chip to chip. "It usually wakes up locked" is NOT a guarantee.
☐ The fix is one line: while reset is active (active-low ~reset), force the lock bit to a known value.
☐ ⚠️ The first write does not close the window, it is the window's END. MITRE does not say 0 or 1: the known value must be the LOCKED one.
☐ Its cousin in software: CWE-457, a variable never given an initial value. Both are under 665.
☐ The difference: in software an undefined value is something LEFT OVER in memory, in hardware it is PHYSICS.
☐ 🔑 Reset value = secure value (fail-secure). Opening should require authority, closing should not.
☐ Where it meets 1245: in 1245 the way out of an undefined state is a reset, in 1271 the reset itself leaves one undefined.
☐ The clock doesn't close the window either (18): both SR Latches in the flip-flop are undefined at power-on, even without flickering. The window ends at the first showing.
```
