# 👾 CWE-480 — Use of Incorrect Operator

> **Using the wrong operator.** The code compiles, gives no warning, and runs.
> But the operator that was written is not the operator that was meant. A
> one-character difference can turn the whole decision upside down.

## One Letter Makes the Difference

In lesson 12 you built four logic operations: AND, OR, XOR, NOT. All of them
worked **bit by bit** — each of the 16 wires went into the operation with its own
partner, and nobody interfered with anybody else.

In C and its descendants these operations come in two separate families, and
they are written almost the same way:

| Written | Name | What it does |
|---|---|---|
| `&` | bitwise AND | The circuit you built in 12: each bit on its own |
| `&&` | logical AND | "are both true" — the result is a single true/false |
| `\|` | bitwise OR | each bit on its own |
| `\|\|` | logical OR | "is either one true" |
| `=` | assignment | **write** the right-hand side into the left-hand side |
| `==` | equality | is the left-hand side **equal to** the right-hand side |

> 🔑 These are not abbreviations of each other, they are **separate operations.**
> Writing one character too few or too many changes the meaning of the code — but
> the compiler usually does not object, because what you wrote is also a valid
> expression.

---

## Bit by Bit, or as a Whole

The simplest example that shows the difference:

```c
int a = 1;   /* binary: 0001 */
int b = 2;   /* binary: 0010 */

a & b    →  0000  →  0        bitwise: no set bit in common
a && b   →  1                 logical: both are non-zero
```

The same two numbers, two operators, **opposite results.** Now put this into a
permission check:

```c
if (kullanici_yetkili & yonetici_modu) { ... }   /* & was written */
```

If `kullanici_yetkili = 1` (0001) and `yonetici_modu = 2` (0010), the result is
**0** — so although both are true, the condition comes out false. The reverse is
possible too: if different flags share a bit, the condition comes out true even
though neither was meant.

The second difference is sneakier: **`&&` short-circuits, `&` does not.**

```c
if (p != NULL && p->deger > 0)   /* if p is NULL the right side NEVER runs */
if (p != NULL &  p->deger > 0)   /* even if p is NULL the right side RUNS → crash */
```

The guard on the left was written to protect the right side. With `&`, the guard
itself is switched off.

## 2003: A Missing Equals Sign in the Kernel

The best-known real case of this weakness was not an accident but **an
attempt.**

In November 2003, two lines that nobody had submitted were found added to the
CVS mirror of the Linux kernel. The condition inside `sys_wait4` was this:

```c
if ((options == (__WCLONE|__WALL)) && (current->uid = 0))
```

At first glance it looks like a check. But the `=` on the right is not `==` — it
is not a comparison but an **assignment.** A process that reached that line wrote
zero into its user ID: in other words, `root`.

What is more, the value of an assignment expression is the value assigned — `0`,
that is, "false". The condition was never true, **but its side effect had already
happened.**

The attempt failed: the kernel was mainly kept in BitKeeper, the CVS mirror was
derived from it, and this change had no counterpart in the main repository. The
inconsistency was noticed by automatic checks.

> 🔑 The lesson here is on the defence side: besides **who wrote** the code, whether
> the repository was consistent with itself also had to be checked — and because
> it was, the change was caught.

## Why the Compiler Stays Quiet

Because what you wrote is **valid code.** `if (x = 5)` is not an error: 5 is
assigned to x, the value of the expression is 5, and since it is non-zero the
condition counts as true. By the rules of the language, everything is fine.

Besides staying quiet, the compiler sets one more trap: `&` and `&&` have
**different operator precedence.**

```c
if (a & b == c)     /* b == c is computed first, then a & (the result) */
if ((a & b) == c)   /* probably what was meant */
```

Forgetting the parentheses produces a third, wrong meaning.

---

## How to Prevent It

- **Turn on warnings.** With `-Wall`, most compilers report the `if (x = 5)`
  pattern as *"suggest parentheses around assignment"*. If you really mean an
  assignment, add extra parentheses — `if ((x = f()))` — the compiler goes quiet
  and the reader understands.
- **Avoid assignments inside conditions.** Put it on its own line: assign first,
  then compare.
- **A Yoda condition is an option:** if you write `if (5 == x)`, then typing `=`
  by mistake gives you a compile error (you cannot assign to a constant). Its
  readability is debatable, but it works.
- **Use a static analyser.** Tools such as `clang-tidy` and `cppcheck` carry rules
  aimed at this family; they catch what the compiler lets through.
- **State your intent in flag checks.** If you are testing a single flag,
  `if (bayraklar & YONETICI)` is right; if you are combining two separate truth
  values, `&&` is right. If you can say in a sentence which one you are doing,
  the operator follows.

## Summary — Keep in Mind

```
☐ & and && are separate operations, not abbreviations of each other. The same for | and ||.
☐ & works bit by bit (the circuit you built in 12), && asks "are both true".
☐ For a=1, b=2: a&b = 0 but a&&b = 1. Same numbers, opposite results.
☐ && short-circuits, & does not: write a NULL check with & and the guard collapses.
☐ = is assignment, == is comparison. if (x = 5) is valid code, the compiler stays quiet.
☐ In 2003 (current->uid = 0) was slipped into the Linux CVS mirror; it was caught through a repository inconsistency.
☐ & and == have different precedence: (a & b == c) does not group the way you expect, add parentheses.
☐ Defence: -Wall, no assignments in conditions, a static analyser, state your intent in a sentence.
```
