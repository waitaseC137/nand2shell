# 👾 CWE-119 — Improper Restriction of Operations within the Bounds of a Memory Buffer

> **Stepping outside the buffer.** A program works on a reserved area of memory,
> but reaches somewhere outside its boundary. The weakness on this page is not a
> single bug but an **umbrella**: it gathers every form of boundary violation.

| | |
|---|---|
| **Official name** | Improper Restriction of Operations within the Bounds of a Memory Buffer |
| **Abstraction level** | *Class* |
| **Parent** | CWE-118 — Incorrect Access of Indexable Resource (*Range Error*) |
| **Its child in the catalogue** | [787](./cwe_787.md) — out-of-bounds write |
| **Where it is born** | [08 · Increment](../salterden_bilgisayara/08_increment.md) — where the overflowed number lands |

---

## 787 Is Half the Story

When [787](./cwe_787.md) entered your catalogue, it entered as the end of a
chain: the number overflows → the size is computed wrong → something is
**written** out of bounds. Near the top of the Top 25 (first in 2021–2023, fifth in 2025), sitting
in Tier 1.

But standing on its own, 787 leaves this impression:

> *"Going out of bounds = writing."*

Look at the umbrella and you see that this is wrong. A buffer's boundary is
described by two questions, and each question has two answers:

```
              BEFORE THE START       AFTER THE END
            ┌────────────────────┬────────────────────┐
   READ     │       125          │        125         │
            ├────────────────────┼────────────────────┤
   WRITE    │       787          │        787         │
            └────────────────────┴────────────────────┘
                    786                  788
```

Four corners. 787 covers only the **bottom row**. The top row —
CWE-125, out-of-bounds read — is much quieter, and it too is in the
Top 25's top ten (eighth in 2025).

> 🔑 Writing breaks things: a value changes, the program crashes, a trace is
> left. **Reading touches nothing.** Something that should not be seen is simply
> seen — and the program keeps running normally. That is why Heartbleed, revealed in 2014 (an
> out-of-bounds read in OpenSSL), went unnoticed for two years.

---

## Three Questions, Ten Children

119 has ten children, and they all fall under three questions. When you see a
boundary violation, ask these three in order:

### ① What did you do?

| CWE | what happens |
|---|---|
| **125** Out-of-bounds Read | Something was **read** from outside — quiet |
| [**787**](./cwe_787.md) Out-of-bounds Write | Something was **written** outside — loud ✓ *you have it* |

### ② Where did you step out?

| CWE | what happens |
|---|---|
| **786** Access Before Start of Buffer | **Before the start** of the buffer |
| **788** Access After End of Buffer | **After the end** of the buffer |

It is tempting to map these two onto the two directions of overflow in your
catalogue, but the direction of the wrap does not decide the direction of the
violation:

```
CWE-190  wrap upward     →  size computed too SMALL  →  the write runs past the end        →  788
CWE-191  wrap downward   →  0 − 1 becomes HUGE       →  index or length runs past the end  →  788
negative signed index    →  buf[-1]                  →  access before the start            →  786
```

Both wraps usually end up in the same place, past the end: in [191](./cwe_191.md)'s
own example, `len - 1` reaches `memcpy` as the largest number of its type. What
usually takes you before the start is not a wrap but a negative index, and what
catches it is the lower-bound check ([CWE-839](./cwe_839.md)). (Added to a full
64-bit pointer, `2⁶⁴ − 1` can wrap the address as well and land just before the
buffer. The cause is still a huge number, not a shrinking index.)

### ③ How did you get there?

You step outside the boundary in one of two ways: either your **calculation** is
wrong, or the **pointer** in your hand is wrong.

| CWE | what happens |
|---|---|
| **805** Buffer Access with Incorrect Length Value | The length was computed wrong |
| **823** Use of Out-of-range Pointer Offset | The offset is out of range |
| **822** Untrusted Pointer Dereference | The pointer came from outside and was not validated |
| **824** Access of Uninitialized Pointer | The pointer was never given a value |
| **825** Expired Pointer Dereference | The pointer was valid once, but not any more |
| **466** Return of Pointer Outside Expected Range | A function returned an out-of-range pointer |

> 💡 Note **825**: *"it was valid once."* 787 and 125 cross the boundary **in
> space**, 825 crosses it **in time**.

## Why It Has Its Own Page

You do not label a real vulnerability with 119; the most concrete level is
chosen ([the hierarchy rule](./README.md#the-hierarchy-between-cwes)). If it is a
write, [787](./cwe_787.md); if it is a read, 125; if it is an expired pointer,
825.

The reason it has a page is the **four-corner table** above. Its only child in
your catalogue is 787, and that page looks like an "out-of-bounds write"
problem. Yet the same root — *reaching outside the buffer* — also shows up in
reading, in overflowing backwards, and in a broken pointer.

Once you see the umbrella, the review question changes:

> Instead of *"Is something written here?"* → *"Is this access inside the
> buffer?"*

The second one covers reading as well as going backwards.

---

## How to Prevent It

- **Ask about the boundary before the access.** A check that looks at the result
  of an overflowed calculation sees the wrapped value (`08.5`). The safest way is to
  ask without letting the overflow happen at all (`a > MAX - b`). For unsigned
  types, a check that deliberately looks for the wrap, `r = a - b; if (r > a)`,
  also catches it afterwards.
- **Check both directions.** Looking only at the upper bound is half a check — a
  negative index passes the upper bound and reaches before the start
  ([CWE-839](./cwe_839.md), `786`). An unsigned index that wrapped downward is huge;
  the upper bound catches that one.
- **Compute the length in one place.** If the same size is recomputed in three
  places, it has to be right in all three (`805`).
- **Carry the boundary with the data.** Instead of a raw pointer, use a type that
  carries "pointer + length" (slices, `span`, `string_view`). If the boundary
  is never lost, it is harder to violate.
- **Ask where the pointer came from.** Treat a pointer from outside as data and
  validate it (`822`); do not use an uninitialised one (`824`); do not hold on to
  it after it has been freed (`825`).
- **Turn on the compiler's and the runtime's checks.**
  `-fsanitize=address,bounds` and bounds checking in debug builds are for
  catching bugs in testing. `_FORTIFY_SOURCE`, on the other hand, is a hardening
  that stays on in production: many distributions build their packages with it.
- **If you can, leave the boundary to the language.** In tools where bounds
  checking is part of the language itself, most of this family ends at compile
  time or in a safe panic.

## Summary — Keep in Mind

```
☐ CWE-119 is a CLASS: any operation that reaches outside the bounds of a memory buffer.
☐ 🔑 787 is HALF the story. Believing "out of bounds = writing" is the most common misreading.
☐ Four corners: READ/WRITE × BEFORE THE START/AFTER THE END. 787 covers only the bottom row.
☐ Writing breaks things and leaves a trace; READING touches nothing, the program keeps running normally.
☐ Three questions: ① WHAT did you do (125 read / 787 write) ② WHERE did you step out (786 before / 788 after) ③ HOW did you get there.
☐ The direction of the wrap is not the direction of the violation: 190 shrinks a size, 191 makes a number huge → both usually 788. What usually leads to 786 is a negative index.
☐ ③ splits in two: a wrong CALCULATION (805 length, 823 offset) or a wrong POINTER (822, 824, 825, 466).
☐ 825 "was valid once". 787/125 cross the boundary IN SPACE, 825 IN TIME.
☐ You do not label a real vulnerability with 119 — the most concrete level is chosen (787, 125, 825...).
☐ The review question changes: NOT "is something written here" but "is this access inside the buffer".
☐ Defence: ask about the boundary BEFORE the access · check BOTH directions · compute the length in one place.
☐ Carry the boundary with the data (pointer + length). If the boundary is never lost, it is harder to violate.
☐ Ask about the pointer's ORIGIN: if it came from outside, treat it as data; do not use an uninitialised one; do not hold on to a dead one.
```
