# 👾 CWE-682 — Incorrect Calculation

> **The calculation is wrong.** The weakness on this page is not a single bug but
> an **umbrella**: a calculation the program performs produces a wrong result, and
> that result later goes into a decision or into allocating a resource.

| | |
|---|---|
| **Official name** | Incorrect Calculation |
| **Abstraction level** | **Pillar** — MITRE's top tier |
| **Parent** | None. Pillars are the top of the hierarchy. |
| **Its children in the catalogue** | [190](./cwe_190.md) · [191](./cwe_191.md) · [193](./cwe_193.md) |

---

## What a Pillar Means

MITRE's CWE list is not a flat list but **a tree with four tiers:**

```
Pillar             most abstract  ·  names a theme                        ·  CWE-682
   └─ Class                        ·  a kind independent of technology
        └─ Base                    ·  concrete enough to give detection and prevention methods
             └─ Variant            ·  specific to a particular technology/language
```

Most of the pages in your catalogue are at the **Base** level: [190](./cwe_190.md),
[193](./cwe_193.md), [787](./cwe_787.md) and so on. For them you can say "watch
out for this, prevent it like that".

682, however, is a **Pillar.** Not a kind of bug but **a heading**: *"the
calculation came out wrong."* Everything under it is a variety of that.

> 🔑 A pillar's job is not to label bugs but **to show kinship.** At first glance
> 190 and 193 look unrelated — one is an overflow, the other a boundary shift.
> 682 says why both belong to the same family: **in both, a number was computed
> wrong.**

---

## The Real Word in the Definition

MITRE's definition is this:

> *"The product performs a calculation that generates incorrect or unintended
> results that are **later used** in security-critical decisions or resource
> management."*

The sentence's centre of gravity is the **"later used"** part.

A wrong calculation on its own is not a security problem. Print a wrong number
on the screen and it is a bug, not a vulnerability. The weakness starts the
moment that wrong number **turns into a decision**:

```
        wrong calculation
               │
      ┌────────┴────────┐
      │                 │
 printed on screen   goes into a DECISION
      │                 │
     bug             WEAKNESS
```

The decision takes one of three forms, and every case in your catalogue is one of
them:

| decision | example |
|---|---|
| **How much space do I reserve?** | the [190](./cwe_190.md) → [680](./cwe_680.md) → [787](./cwe_787.md) chain |
| **Is this value inside the bound?** | [839](./cwe_839.md), [193](./cwe_193.md) |
| **Where do I write / read?** | index and pointer calculations |

> 💡 This was exactly the sentence in lesson 08's *Security Bridge* section: the
> overflowed number does not break anything — **asking the overflowed number a
> question** does.

## Pillars Are Not Labels

A practical rule: **you do not label a real vulnerability with 682.**

Pillars are so abstract that saying "this is a calculation bug" does not get you
much further than saying "this is a software bug". When a CVE is assigned a
number, the **most concrete** tier possible is chosen: Base-level numbers such as
190, 193, 131.

A pillar has a different function:

- **For orientation.** When you see a new calculation bug, you check "where in
  this family does it fall".
- **For drawing the scope of an audit.** The question *"What from the 682 family
  could be in this code?"* gives a more complete sweep than searching for
  190/191/193 one by one.
- **For seeing the kinship.** If the same defence can close the whole family at
  once, you only notice it by looking at the umbrella.

---

## How to Prevent It

At the umbrella level the defence is at the umbrella level too — the details are
on each child's page, but the shared pattern is this:

- **Ask about the bound before doing the calculation.** This is the answer to
  almost this whole family: will it overflow, will it fit, will it go negative —
  **before you see the result.**
- **Validate the result before it goes into a decision.** If the output of the
  calculation will be a memory size, an index or a bound, it should be tested
  once more before it gets there.
- **Use tools that catch overflow.** Compiler options such as `-ftrapv` and
  `-fsanitize=undefined` make an overflowing calculation shout at run time
  instead of slipping through silently.
- **Prefer checked arithmetic functions.** GCC/Clang's `__builtin_add_overflow`
  family returns whether it overflowed alongside the result — removing the
  "compute first, look later" trap.
- **Use types with a known width and sign.** Most of this family's cases feed on
  the uncertainty of "which type was it, how many bits".
