# 👾 CWE-1245 — Improper Finite State Machines (FSMs) in Hardware Logic

> **The state the designer did not care about.** A state machine in hardware has
> not defined every state that can occur. The state left undefined was thought of
> as "it never happens anyway". But if it does, the circuit falls somewhere
> unpredictable, and only a reset gets it out.

| | |
|---|---|
| **Official name** | Improper Finite State Machines (FSMs) in Hardware Logic |
| **Abstraction level** | *Base* |

## What a State Machine Is

The circuits you built until now had no **state**. The output depended only on
the current input. Give the adder the same two numbers and you get the same sum
every time.

In a state machine, the output depends on two things: **the input** and **which
state the circuit is in right now.** The input moves the circuit from one state
to another.

The SR Latch you built is the smallest possible state machine:

```
states:   Q = 0      Q = 1

inputs and transitions:
   s r
   1 0   →  whatever state you are in, go to Q = 1
   0 1   →  whatever state you are in, go to Q = 0
   1 1   →  stay where you are
   0 0   →  ???  "not used"
```

Two states, four inputs, eight transitions. Six of the eight transitions are
defined. But two of them appear in the table as "not used".

---

## "Not Used" Is Not an Answer

MITRE describes the consequence of this weakness like this:

> *"Faulty FSM designs that do not account for all states, either through
> undefined states (**left as don't cares**) or through incorrect implementation,
> might lead an attacker to drive the system into an **unstable state** from which
> the system cannot recover without a reset."*

*Don't care* is a shorthand used often in design. The designer says of a row:
"this input never arrives, and if it does, what happens does not matter."

The `0 0` row in the SR Latch is exactly a *don't care*. But as you saw in
[lesson 16](../salterden_bilgisayara/16_sr_latch.md#the-unused-row), the circuit
keeps doing something in that row:

```
while 0 0:                    both gates are 1   ← two outputs that should be opposites are EQUAL
both inputs go to 1 at once:  both drop to 0
                              both go back to 1
                              ...                ← flicker; where it will end up is unknown
```

Two outputs that should carry opposite values show the same value, and the
circuit is left unstable as it leaves this row. That is the *unstable state* in
MITRE's sentence.

> 🔑 **The row the designer does not care about is the row the attacker cares
> about.** An input declared "it never happens anyway" is the most interesting
> input for someone who sends it on purpose.

---

## Why It Is a Security Matter

The latch in NandGame holds one bit, and that bit means nothing. On a real chip,
however, state machines often hold **the security state**. In MITRE's words:
*"FSMs can be used to indicate the current security state of the system."*

Examples:
- Is the debug interface **locked or open**
- Has boot verification **finished or not**
- Is the processor **in privileged mode**

If such a machine is pushed into an undefined state, two outcomes are possible.
MITRE lists both:

| outcome | what happens |
|---|---|
| **Denial of service** (DoS) | The machine hangs and only a reset rescues it |
| **Privilege gain** | The undefined state behaves like the "open" state |

---

## MITRE's Example

The example on MITRE's page is written in a hardware description language
(Verilog). You do not need to know the language; the idea is simple:

```
input is 3 bits    →  it can take 8 different values (0 … 7)
the code covers    →  0 … 5
it does not cover  →  6 and 7                    ← don't care
```

The fixed version of the code adds a single line:

```verilog
default: state = 2'h0;
```

In other words: *"If an input you do not recognise arrives, go back to a known,
safe state."*

This example recalls the count in [lesson 14](../salterden_bilgisayara/14_alu.md).
There the control word produced 32 states and the documentation described 8. On
the [CWE-1242](./cwe_1242.md) page we called the difference *"a place to look"*.
1245 is the same difference in a state machine:

```
14 · ALU        the documented operation space  ⊂  the real operation space   →  1242
16 · SR Latch   the defined state space         ⊂  the real state space       →  1245
```

## Its Cousin in Software

The closest counterpart of the same bug in software is a `switch` with no
`default`: **CWE-478** — *Missing Default Case in Multiple Condition Expression*.
MITRE put it under [CWE-1023](./cwe_1023.md) (incomplete comparison). Not all
possible cases were looked at, and in the case that was not looked at, the
program silently does something.

It has a cousin on the loop side too: an unchecked input goes into a loop
condition (**CWE-606**) and the loop never ends (**CWE-835**). The latch's flicker
as it leaves `0 0` is the hardware image of this, but there is a difference: in
835 the loop was built by the programmer. In the latch, the loop is the circuit
itself.

---

## Why the D Latch Exists

The level that comes after the SR Latch, the **D Latch**, can be read as the fix
for this weakness. First the general picture: there are two roads.

```
① Define what happens if the undefined row arrives        →  MITRE's "default" fix
② Build an input in which the undefined row CANNOT OCCUR  →  removing the problem at the root
```

The second is stronger, because it removes the question "what do I do if it
arrives".

The D Latch takes the second road. It derives the SR Latch's two commands from a
single data wire, one from the wire itself and the other from its inverse. Since
a wire and its inverse can never both be 1, the two opposing commands can never
arrive at the same time either. The `0 0` row **cannot occur by construction**.
How it is built →
[17 · D Latch](../salterden_bilgisayara/17_d_latch.md#the-forbidden-row-is-gone)

> 🔑 Baking the rule into the shape of the circuit instead of leaving it to the
> user. A document that says "do not do this" protects only as far as it is read.
> A structure that makes it impossible does not need anyone to read it.

---

## How to Prevent It

- **Define every state.** MITRE's advice: *"Define all possible states and handle
  all unused states through default statements."* An `n`-bit input means `2ⁿ`
  rows. Leave no empty row in the table.
- **Make the default state the secure state.** *"Ensure that system defaults to a
  secure state."* If something you do not recognise happens, fall to the
  **locked** side, not the open side.
- **If possible, make the forbidden state impossible.** Build the input so that
  the undefined combination can never occur. Better than a defined escape route is
  a design that needs no escape.
- **Return to a known state on reset.** If the only way out of an undefined state
  is a reset, the reset must not leave the machine somewhere uncertain either
  ([CWE-1271](./cwe_1271.md)).
- **Scan the whole state space during verification.** Test not the documented
  transitions but **all possible** transitions. In hardware there are tools that do
  this (*formal verification*), and they were designed for this job.
