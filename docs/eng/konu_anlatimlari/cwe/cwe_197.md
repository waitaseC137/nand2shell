# 👾 CWE-197 — Numeric Truncation Error

> **Numeric truncation error.** A wide number is put into a narrow place. The
> upper bits that do not fit are silently dropped. What remains is a small piece
> of the same number — and nothing complains.

| | |
|---|---|
| **Official name** | Numeric Truncation Error |
| **Parent** | [CWE-681](./cwe_681.md) — Incorrect Conversion between Numeric Types |
| **Where it is born** | [13 · Arithmetic Unit](../salterden_bilgisayara/13_arithmetic_unit.md#a-16-bit-1-is-not-one-wire) — a matter of width |
| **Its mirror** | [CWE-194](./cwe_194.md) — the opposite direction: narrow → wide (sign extension) |

## Where the Bits That Do Not Fit Go

[194](./cwe_194.md) asked, while widening a narrow number, **what should be put
into the empty bits**. Here we go the other way: a wide number is entering a
narrow place, and the question is — **what happens to the bits that do not
fit?**

The answer: they are dropped.

```c
int   i = 300;      /* 0000 0001 0010 1100 */
char  c = i;        /* the low 8 bits remain:  0010 1100  →  44 */
```

```
  300  =  0000 0001 0010 1100
              └┬─┘  └───┬───┘
           dropped   left  =  44
```

Truncation is a close relative of [CWE-190](./cwe_190.md) (overflow), but it is
not the same thing:

| | what happens |
|---|---|
| **CWE-190** overflow | the number exceeds the limit of **its own type** and wraps around |
| **CWE-197** truncation | the number loses its upper bits while being moved into **another type** |

In both the result is "a smaller number than expected", but one is born in a
calculation and the other in a copy.

> 🔑 The sneakiest thing about truncation is its **silence.** No error is
> returned, no flag goes up, the compiler does not warn with default settings.
> The assignment looks successful — only the number inside it is now a different
> number.

---

## A Shrunken Number Fools the Check

Its dangerous form is truncation sitting **between the check and the use**.

```c
int uzunluk = istekten_oku();        /* 65536 arrived */

if (uzunluk > sizeof(buf)) return HATA;   /* 65536 > 16 → returns HATA, good */
```

No problem so far. But if the check and the use are done with types of different
widths:

```c
int            uzunluk = istekten_oku();   /* 65536 */
unsigned short kisa    = uzunluk;          /* low 16 bits → 0 */

if (kisa > sizeof(buf)) return HATA;       /* 0 > 16 is false → PASSES */
memcpy(buf, veri, uzunluk);                /* but the copy is 65536 bytes */
```

The check looks at the **truncated** value, the use looks at the **full** value.
They were assumed to be the same number; they are not.

> ⚠️ Repeat the sentence this family shares: *there was a check, but it did not
> help.* [190](./cwe_190.md) got the order wrong (the question was asked of an
> overflowed number) · [839](./cwe_839.md) is missing half (only the ceiling was
> checked) · [367](./cwe_367.md) got the moment wrong (a change slipped in
> between) · **197 gets the width wrong** (the question is narrow, the use is
> wide).

## In Real Life

The most concrete examples of this weakness show up in **protocol and file
headers**, because there the field widths are fixed and the code has to copy
them into its own types.

The hands-on form of this is already written on the exploit side of the repo:
[binary_exploitation/11 · Integer Bugs](../binary_exploitation/11_integer_bug_truncation_signedness.md)
— the **Utumno 4** level is built directly on truncation, and in **Maze 7** a
16-bit field read from the ELF header is used directly as the read size.

The hunter's question from the same lesson holds here too:

> **With which type is the size/bounds check done?** If the check is on a
> `word` or a `byte` and the use is on a wider type — there is truncation in
> between.

On a historical scale its best-known relative is **Y2K**: because the year field
was truncated to two digits, 2000 could not be told apart from 1900. The same
pattern — the field carrying the information was narrower than the information
itself.

## How to Prevent It

- **Before truncating, ask whether it fits.** This is the only real defence in
  this family:

  ```c
  if (uzunluk < 0 || uzunluk > USHRT_MAX) return HATA;
  unsigned short kisa = (unsigned short)uzunluk;
  ```

- **Use the same type for the check and the use.** Most cases begin with the
  sentence "the same value travels around in two different widths". Choose a
  type once and carry it everywhere.
- **Use types with a known width.** `uint16_t`, `int32_t`, `size_t`. How many
  bits an `int` has changes with the platform; that uncertainty makes truncation
  invisible.
- **Make the compiler say it.** `-Wconversion` turns narrowing assignments into
  warnings. It is off by default.
- **Look twice at sizes from outside sources.** Every length field coming from
  the network, a file or the user should be tested before it enters its own
  type.

## Summary — Keep in Mind

```
☐ Moving wide → narrow, the UPPER bits that do not fit are silently dropped. 300 → 8 bits = 44.
☐ No error returns, no flag goes up, the default compiler does not warn. The assignment looks successful.
☐ CWE-190 is overflow (in its own type), CWE-197 is truncation (when moving into another type). Different.
☐ The danger is truncation getting BETWEEN THE CHECK and THE USE.
☐ If the check looks at the truncated value and the use at the full value, the check protects nothing.
☐ The "there was a check but it did not help" family: 190 the order · 839 half · 367 the moment · 197 the width.
☐ It is 194's mirror: that one is narrow→wide (the sign extends), this one wide→narrow (the upper bits go).
☐ Y2K is the same pattern: the year field was narrower than the year itself.
☐ Defence: ask about the bound before truncating, use the SAME type for the check and the use.
```
