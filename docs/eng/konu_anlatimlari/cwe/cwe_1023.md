# 👾 CWE-1023 — Incomplete Comparison with Missing Factors

> **The comparison asks too little.** Comparing two things requires looking at
> more than one factor. The code skips asking about one or more of them — and the
> skipped factor is the one that would change the answer.

| | |
|---|---|
| **Official name** | Incomplete Comparison with Missing Factors |
| **Abstraction level** | *Class* |
| **Parent** | [CWE-697](./cwe_697.md) — Incorrect Comparison (*pillar*) |
| **Its child in the catalogue** | [839](./cwe_839.md) — the lower bound check is missing |

---

## A Missing Question, a Confident Answer

The sneaky part of this family is this: **there is a check.** The code asks
something, gets an answer, and decides according to that answer. In an audit it
gets ticked off as "a check is made here" and passed.

But the question asked is incomplete:

```
  asked:      "is this value below the ceiling?"
  not asked:  "and is it above the floor?"
```

The answer comes back "yes" and it is right — for the question that was asked.
What is wrong is not the answer but **the scope of the question.**

> 🔑 There is a sentence that repeats in your catalogue: *"there was a check, but
> it did not help."* 1023 is **one kind** of reason for that sentence —
> [190](./cwe_190.md) got the order wrong, [367](./cwe_367.md) got the moment
> wrong, [197](./cwe_197.md) got the width wrong, **and 1023 has an incomplete
> scope.**

---

## Its Four Forms

What MITRE lists under this class shows how many kinds of "incomplete" there can
be:

| CWE | What is missing |
|---|---|
| [**839**](./cwe_839.md) — Numeric Range Comparison Without Minimum Check | **One end** of the range ✓ *you have it* |
| **187** — Partial String Comparison | Only part of the string is compared, not **all** of it |
| **184** — Incomplete List of Disallowed Inputs | The deny list is **incomplete** — a road was left uncounted |
| **478** — Missing Default Case | A multi-way branch has no case for **the unexpected situation** |

**187 (partial string comparison)** deserves special attention: comparing only
the first few characters of a password or a signature lets the attacker search
for the right answer character by character. This is a pattern you know from
elsewhere in your catalogue — the "avoid comparisons that exit early" item in
[1300's defence list](./cwe_1300.md) is the timing and power side of the same
wound.

**184 (incomplete deny list)** teaches the same lesson as the defence of
[706](./cwe_706.md): *"count what is allowed instead of counting what is
forbidden."* A deny list is always incomplete, because there are more spellings
than you can count.

## The Connection to Flags

In [lesson 10](../salterden_bilgisayara/10_bayraklar.md) you built the machine's
way of saying "if": a comparison is really **a subtraction + looking at the
flags**.

That lesson gives the circuit side of this class. When you build a comparison in
hardware you see this: **you choose which flag to look at.** Look at the zero
flag but not at the sign flag, and you have asked "is it equal" but not "is it
less".

> 💡 The software side of 1023 is "a missing `if`", the hardware side is "a flag
> that was not read". The same omission, two layers.

Its parent, **CWE-697 (Incorrect Comparison)**, is now in your catalogue; it was
written together with NandGame's **Condition** level. 697 splits comparison bugs
into three questions — *what* was compared, was it *enough*, *how* was it
compared — and 1023 is its "not enough" branch. The OF debt closed in lesson 15
lands here too: looking at the sign bit and not at the overflow flag is a missing
factor.

---

## Why It Has Its Own Page

You do not label a real vulnerability with 1023; the most concrete tier is
chosen ([the hierarchy rule](./README.md#the-hierarchy-between-cwes)).

The reason it has a page is this: its only child in your catalogue
([839](./cwe_839.md)) looks like a problem of numeric ranges. Yet the same
omission also shows up in strings (187), in lists (184) and in branching (478).
Once you see the pattern, the audit question changes:

> Instead of *"Is there a check here?"* → *"How many **factors** does this check
> look at, and how many should it have looked at?"*

---

## How to Prevent It

- **Ask about the range from both ends.** The lower bound and the upper bound,
  separately. A one-sided check is the most common case in this family.
- **Compare fully, do not exit early.** For secret values such as passwords,
  signatures and digests, use a constant-time comparison — both the omission and
  the leak are closed.
- **Keep an allow list, not a deny list.** A deny list is doomed to be
  incomplete.
- **Write the default case.** There should always be a branch for the unexpected
  situation, and it should fall on the safe side.
- **Write the scope of the check as a sentence.** If you can say *"this check
  guarantees these three things"*, you can also see what is missing.

```
☐ What is wrong is not the answer but THE SCOPE OF THE QUESTION.
☐ The "there was a check but it did not help" family: 190 the order · 367 the moment · 197 the width · 1023 the SCOPE.
☐ Its four forms: 839 (one end of the range) · 187 (part of a string) · 184 (incomplete deny list) · 478 (no default case).

```
