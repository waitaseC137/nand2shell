# 👾 CWE-670 — Always-Incorrect Control Flow Implementation

> **The path is always wrong.** There is a control-flow path in the code, and that
> path does not reflect the algorithm it is supposed to implement. It behaves
> wrongly not sometimes, but **every time it is taken**.

| | |
|---|---|
| **Official name** | Always-Incorrect Control Flow Implementation |
| **Abstraction level** | *Class* |
| **Parent** | CWE-691 — Insufficient Control Flow Management |
| **Its child in the catalogue** | [480](./cwe_480.md) — incorrect operator |

---

## The Word "Always" Matters

The *always* in its name is what sets this class apart. Some weaknesses in your
catalogue produce **conditional** failures:

| | when it breaks |
|---|---|
| [CWE-362](./cwe_362.md) race condition | Only if the timing lines up |
| [CWE-190](./cwe_190.md) overflow | Only if the number grows large enough |
| [CWE-1261](./cwe_1261.md) bit flip | Only if a particle hits |
| **CWE-670** | **Every time** |

That sounds like good news — you think "if it is always broken, it is easy to
catch". In practice it can be the opposite:

> 🔑 The path is **always wrong**, but it may be that **the path is rarely
> taken**. The faulty branch is the one that runs once a year, in one special
> case. When that branch is entered the behaviour is certainly wrong — but until
> that day no test ever went there.

---

## Its Six Forms

What MITRE lists under this class shows how many ways there are for "the code you
wrote is not the algorithm you meant":

| CWE | What happens |
|---|---|
| [**480**](./cwe_480.md) — Use of Incorrect Operator | `&&` instead of `&`, `=` instead of `==` ✓ *you have it* |
| **783** — Operator Precedence Logic Error | The operators are right, the **grouping** is wrong |
| **483** — Incorrect Block Delimitation | The block boundary is wrong: no curly braces |
| **484** — Omitted Break Statement in Switch | The case does not end, it **falls through** into the next |
| **617** — Reachable Assertion | A reachable assertion stops the program |
| **698** — Execution After Redirect | A redirect was issued but the code **kept going** |

Note **783** in particular — the `if (a & b == c)` trap described on
[480's page](./cwe_480.md#why-the-compiler-stays-quiet) is exactly this. There
the operators are written correctly; only the assumption about which runs first
is wrong. 480 and 783 are siblings: one is the wrong operator, the other the
wrong order of the right operators.

The best-known form of **483** is a block assumed to be a single line because no
curly braces were used:

```c
if (kontrol_basarisiz)
    hata_yaz();
    return HATA;     /* indented but NOT in the block — it always runs */
```

The indentation fools the reader; the compiler does not look at indentation. In
the real world this pattern has led to cases where critical security checks were
switched off.

---

## Why the Compiler Does Not Catch It

The shared cause behind this whole class:

> **What you wrote is valid code.**

`if (x = 5)` is not an error, it is an assignment. `if (a & b == c)` is not an
error, it is grouped differently. The second line of an `if` without braces is
not an error, it is outside the block. By the rules of the language all of them
are flawless — the flaw lies **in the gap between them and the author's
intent.**

The compiler does not know the intent. That is why the defence for this family
comes not from the compiler but **from writing discipline and extra tools.**

---

## Why It Has Its Own Page

You do not label a real vulnerability with 670; the most concrete level is
chosen ([the hierarchy rule](./README.md#the-hierarchy-between-cwes)).

The reason it has a page is this: its only child in your catalogue is
[480](./cwe_480.md), and that page looks like a problem of "mixing up
operators". Yet the same root — *the intent and the code drifting apart* — also
shows up in parentheses, in indentation, in a `switch` case and after a
redirect.

Once you see the pattern, the review question changes:

> Instead of *"Is this code correct?"* → *"Does this code do what its author
> **describes**?"*

---

## How to Prevent It

- **Turn on warnings and raise them to errors.** `-Wall -Wextra` catches most of
  this family: assignment in a condition, ambiguous parentheses, a missing
  `break`.
- **Always use curly braces.** Even for a one-line block. This rule removes 483
  completely.
- **Write the grouping out with parentheses.** Do not try to memorise the
  precedence table; parentheses tell both you and the reader the intent (783).
- **Use a static analyser.** `clang-tidy`, `cppcheck`, the language's own linter.
  They catch what the compiler lets through.
- **Have someone explain the code.** The bugs of this family come from the gap
  between the one who reads the code and the one who runs it. Explain it out loud
  and you hear the divergence.
