# 👾 CWE-704 — Incorrect Type Conversion or Cast

> **Something broke while being turned into something else.** The program moves
> an object, a resource or a structure from one type to another. If the
> conversion is done wrong, what you have in your hand is no longer what you
> think it is — it is something else.

| | |
|---|---|
| **Official name** | Incorrect Type Conversion or Cast |
| **Abstraction level** | *Class* |
| **Parent** | CWE-664 — Improper Control of a Resource Through its Lifetime |
| **Its child in the catalogue** | [681](./cwe_681.md) — and the four pages under it |

---

## What a Type Is, and Why It Exists

The sentence you learned in [lesson 04](../salterden_bilgisayara/04_teller_sayi_olunca.md)
holds here too: **wires claim nothing.** The pattern sitting on 16 wires is just
a pattern until someone says what it is.

A type is **the contract for how that pattern is to be read**: how many bits
wide, signed or not, a number or an address, part of which structure.

A conversion (*cast*) is changing the contract. And here is the danger:

> 🔑 **A conversion does not change the data, it changes the rule for reading the
> data.** The same bits stay, the rule looking at them is new. If the wrong rule
> is chosen nothing breaks — everything is simply misunderstood.

---

## A Three-Step Ladder

704 sits at the top of the deepest hierarchy in your catalogue. You have three
tiers of it at once:

```
CWE-704   Incorrect Type Conversion or Cast          (Class)
   └─ CWE-681   Incorrect Conversion between         (Base)
                Numeric Types
        ├─ 196   unsigned → signed      the interpretation changes
        ├─ 195   signed → unsigned      the interpretation changes
        ├─ 194   sign extension         the width changes
        └─ 197   truncation             the width changes
```

The difference matters:

- **681 deals only with numbers.** A conversion between two numeric types.
- **704 covers everything:** objects, pointers, structures, resources. It does
  not have to be a number.

> 💡 If the [hierarchy section in the README](./README.md#the-hierarchy-between-cwes)
> feels abstract, this ladder is its tangible form: Class → Base → and under it
> four separate concrete cases.

---

## The Children Outside Numbers

681 is written in your catalogue. 704's other three children show what happens
outside the world of numbers:

**CWE-843 — Access of Resource Using Incompatible Type ('Type Confusion').** The
most dangerous of this family. An area of memory is allocated as one type, then
used as **another type**. The fields of the second type land on top of the
first type's data:

```
allocated:   [ number ][ number ][ number ]
read as:     [     pointer      ][ number ]
                    ↑
       the number the attacker put there is now read as an ADDRESS
```

It is one of the most exploited vulnerability classes in browser and scripting
language engines — because there the same area of memory keeps hosting objects
of different types.

**CWE-588 — Attempt to Access Child of a Non-structure Pointer.** Treating a
pointer that is not a structure as if it were one and accessing its field. A
narrower form of 843.

**CWE-1389 — Incorrect Parsing of Numbers with Different Radices.** The same text
gives a different number when read in a different base: `010` is 8 if read as
octal, 10 if read as decimal. If two components parse the same text in different
bases, a silent disagreement is born between them.

---

## Why It Has Its Own Page

You do not label a real vulnerability with 704 — the class level is too abstract,
the most concrete tier is chosen
([the hierarchy rule](./README.md#the-hierarchy-between-cwes)).

The reason it has a page is different: **681 and the four pages under it are only
one branch of 704.** Stay inside that branch and you will think "a conversion
bug" means "a numeric conversion bug". Yet the same root gives much harsher
results in pointers and objects.

There is also this: **681's parent is not 682 but 704.** This was where an
assumption made while writing the catalogue fell apart — "a calculation bug" and
"a conversion bug" are separate branches. Computing a number wrongly and reading
it wrongly are different things.

---

## How to Prevent It

- **Do not leave the conversion hidden.** Languages perform most conversions on
  their own; writing them explicitly lets the reader and the compiler see them.
- **Ask before converting.** The shared sentence of every page in this family:
  the question *"does it fit, is it suitable"* is asked **before** the conversion.
  Ask afterwards and you are asking a value that has already shifted.
- **Carry the type information with the data.** This is the antidote to 843:
  which type an object is should be written somewhere independent of the code
  looking at it — a tagged union, a virtual type field, the language's run-time
  type checking.
- **Make the compiler say it.** `-Wconversion`, `-Wsign-conversion`, and, in
  type-safe languages, raising the warnings to errors.
- **Carry the same value around with a single type.** Most cases in this family
  begin with the sentence "the same thing travels around with two different
  types".

## Summary — Keep in Mind

```
☐ CWE-704 is a CLASS: something converted wrongly from one type to another.
☐ Type = the CONTRACT for how a pattern is to be read (the sentence from lesson 04).
☐ A conversion does not change the data, it changes the RULE FOR READING the data.
☐ You have three steps: 704 (class) → 681 (base) → 194/195/196/197 (concrete cases).
☐ 681 is only NUMBERS; 704 is objects, pointers, structures, resources — all of them.
☐ 681's parent is NOT 682 but 704: "computing wrongly" and "reading wrongly" are separate branches.
☐ Its most dangerous child is CWE-843 Type Confusion: an area allocated as one type, read as another.
☐ In 843, the NUMBER the attacker put there can be read as an ADDRESS in the second type.
☐ The others: 588 (treating a non-structure as a structure) · 1389 (parsing in a different base).
☐ Defence: write the conversion explicitly · ask first · carry the type information with the data · use one type.
```
