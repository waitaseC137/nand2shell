# 🔄 From Switches to a Computer — Interlude: A Number or a Command?

> The Memory unit is finished, and the Processor unit hasn't opened yet. This
> interlude sits between the two, and it wasn't built from a topic list but from
> four questions asked in exactly this gap:
>
> 1. Where does `cl` come from?
> 2. Where do `op0`, `op1`, `st`, `ad` come from?
> 3. In Counter, where does the register's output go?
> 4. When a number becomes a command, does it stay a number?

> The whole claim of this lesson in one sentence:
>
> **Bits carry no label saying "I am data" or "I am a command". A number in memory
> becomes a command when its bits are wired to control wires.**

## Wires From the Outside

Every circuit you built had inputs, and you always set them to 0 or 1 by hand. Put
them all in one table:

| wire | first seen in | what it tells the circuit |
|---|---|---|
| `op0`, `op1` | [12](./12_logic_unit.md) | which operation to do |
| `s`, `r` | [16](./16_sr_latch.md) | pull the bit to 1 or to 0 |
| `st` | [17](./17_d_latch.md) | whether to write |
| `cl` | [18](./18_data_flip_flop.md) | when |
| `ad` | [21](./21_ram.md) | which word |

> ⚠️ **These are not parts.** Parts, the components, are the boxes: `nand`,
> `register`, `select 16`. `op0`, `st`, `cl` are the **names of the wires** going
> into those boxes. Their technical name is **control signal**: a wire that tells
> a box what to do.

Where do these wires come from? You have already seen the first half of the answer.
In [17](./17_d_latch.md#the-translation-table) you stopped taking `s` and `r` from
outside: you produced both of them yourself from `d` and `st`. At that level `s` and
`r` stopped being external inputs and became wires born inside the circuit.

> 🔑 **Every level takes some of the previous level's external inputs inside.** A wire
> you set by hand from outside is produced from other wires one floor up.

The external inputs left over come in three kinds:

| kind | wires | what they carry |
|---|---|---|
| **data** | `X`, `Y` | the numbers being operated on |
| **control** | `op0`, `op1`, `st`, `ad` … | what to do |
| **time** | `cl` | when to do it |

You met the data/control split in [14](./14_alu.md#data-bits-and-control-bits):
`X` and `Y` are the material, the control wires are the instruction. In the
Processor unit it's the turn of these remaining external inputs.

## Who Holds the Bell?

Of the three kinds, `cl` is unlike the others. You met the clock in
[18](./18_data_flip_flop.md#the-clock-everyone-listens-to-the-same-bell): a wire that
keeps going 0, 1, 0, 1. In the game you flip it by hand.

The question was answered with this intuition: *"the `cl` signals are being repeated
by some other unit; it acts like a signal generator and sends a clock signal."*

Correct. `cl` is not the output of any gate. There is no `nand` inside the circuit
that produces it. A **clock generator** outside, ticking at regular intervals,
supplies it. In real computers that generator is a crystal vibrating at a fixed rate.

> 🔑 **`cl` is the signal the circuit does not produce itself.** Control wires start
> coming from inside as the floors rise. The bell, in a real computer too, comes from
> outside the circuit.

## Follow the Wire

Two small things first.

**Bit = wire.** A bit is a 0 or a 1 on one wire. Put 16 wires side by side and they
carry a 16-bit number. A bundle of wires working side by side is called a **bus**.
Both data and control travel on these buses.

**The counter.** In [20](./20_counter.md) you built a counter: the `register` holds
the number, `inc 16` adds 1 to it, and `select 16` looks at `st` and picks either `X`
or the incremented number.

Now start at the register's output and follow the wire:

```
register  ─▶  inc 16  ─▶  select 16  ─┐
   ▲                                  │
   └──────────────────────────────────┘
```

The wire leaves the `register`, passes through `inc 16` and `select 16`, and returns
**to the `register`'s own input**. On every bell the register reads its own old
value, does something to it, and writes the result back into itself. This is a
**loop.**

> ⚠️ **The loop is inside Counter, not inside RAM.** In [21](./21_ram.md) the
> registers' outputs went to `select 16`, came out at Output, and never returned.
> RAM holds numbers; it doesn't work on them.

Right now there is only a `+1` in the middle of the loop. Imagine putting the **ALU**
from [14](./14_alu.md) in the middle instead of `+1`:

```
Counter:     register ─▶  +1  ─▶ register
Processor:   register ─▶  ALU ─▶ register
```

Now the loop doesn't just add 1 on every bell; it can add, subtract, AND, OR.

The difference between the two units is in this picture:

- **00–15:** circuits that flow one way, from input to output. When the input
  changes, the output changes; nothing is stored.
- **16–21:** circuits that store the result. A value stays inside the loop.

The Processor combines the two: the output of the computing circuit is **written back
into memory.** The model built at the entrance of this unit was: *"Now we'll compute
with what we stored."* The loop is how that happens.

## When a Number Becomes a Command

How will the ALU know **which** operation to do on each bell? In
[14](./14_alu.md#data-bits-and-control-bits) there were five wires saying exactly
that, a **control word**:

```
  u  op1  op0  zx  sw
```

Until now you set these wires by hand. But now you have a memory that stores
numbers. If you wire the bits of a number in memory to these wires, that number
becomes a **command**.

And right here this question was asked:

> *"Will the number that became a command keep its state as a number and give the
> command as a number, or will it now carry on existing as a command?"*

**The number always stays a number.** Nothing changes in memory; the same 16 bits sit
in the same place. What makes it a command is not the number itself, but **which
wires its bits are connected to.**

The same word in memory:

| where the word's bits go | what the word becomes |
|---|---|
| into the ALU's `X` input | **data:** a number to be processed |
| into control wires like `op0`, `op1`, `st` | **command:** a job to be done |

> 🔑 **There is no label on the bits saying "I am a command".** The rule from
> [14](./14_alu.md#data-bits-and-control-bits): there is no physical difference
> between a control bit and a data bit; the difference is where it's connected. The
> rule holds for numbers in memory too: whether a word is data or a command is
> decided by the circuit that reads it.

As you saw in [12](./12_logic_unit.md#who-holds-the-meaning), behavior comes from the
connection and meaning comes from an agreement. Saying "this word is a command" is
an agreement too: the circuit that wires the word to the control wires is the one
that decides to read it as a command.

> 💡 This idea is called the **stored program**: commands and data sit in the same
> memory, as the same kind of numbers. This arrangement is called the **von Neumann
> architecture**. Nearly every computer today works this way.

## Entering the Processor

You hold three pieces:

| piece | from |
|---|---|
| **loop:** register → computation → register | [20](./20_counter.md) |
| **command:** a number whose bits are wired to control wires | this lesson |
| **counter:** one step per bell | [20](./20_counter.md) |

The Processor unit brings these three together. Take these questions with you into
the levels. The answers aren't here, they're in the levels:

1. To read commands lying one after another in memory **in order**, which number
   needs to be held, and by whom?
2. **Which wires** will a command's bits go to?
3. Does `cl` keep coming from outside until the end of the unit? Check while the
   level is open.
