# 👾 CWE-480 — Use of Incorrect Operator

> **Yanlış işleç kullanımı.** Kod derlenir, uyarı vermez, çalışır. Ama yazılan
> işleç, kastedilen işleç değildir. Tek karakterlik fark, bütün kararı ters
> çevirebilir.

| | |
|---|---|
| **Resmî ad** | Use of Incorrect Operator |
| **Üst sınıf** | [CWE-670](./cwe_670.md) — Always-Incorrect Control Flow Implementation |
| **Nerede doğar** | [12 · Logic Unit](../salterden_bilgisayara/12_logic_unit.md) — bit bit çalışan işlemler |
| **Akrabası** | [CWE-697](./cwe_697.md) — yanlış karşılaştırma |

---

## Bir Harf Fark Eder

12. derste dört mantık işlemini kurdun: AND, OR, XOR, NOT. Hepsi **bit bit**
çalışıyordu — 16 telin her biri kendi komşusuyla işleme giriyor, kimse kimseye
karışmıyordu.

C ve türevlerinde bu işlemlerin iki ayrı ailesi var ve yazılışları neredeyse
aynı:

| Yazılış | Adı | Ne yapar |
|---|---|---|
| `&` | bit bit AND | 12'de kurduğun devre: her bit ayrı ayrı |
| `&&` | mantıksal AND | "ikisi de doğru mu" — sonuç tek bir doğru/yanlış |
| `\|` | bit bit OR | her bit ayrı ayrı |
| `\|\|` | mantıksal OR | "biri doğru mu" |
| `=` | atama | soldakine sağdakini **yaz** |
| `==` | eşitlik | soldaki sağdakine **eşit mi** |

> 🔑 Bunlar birbirinin kısaltması değil, **ayrı işlemler.** Tek bir karakter eksik
> ya da fazla yazmak, kodun anlamını değiştirir — ama derleyici çoğu zaman
> itiraz etmez, çünkü yazdığın şey de geçerli bir ifadedir.

---

## Bit Bit mi, Bütün mü

Aradaki farkı gören en basit örnek:

```c
int a = 1;   /* ikilik: 0001 */
int b = 2;   /* ikilik: 0010 */

a & b    →  0000  →  0        bit bit: ortak set bit yok
a && b   →  1                 mantıksal: ikisi de sıfırdan farklı
```

Aynı iki sayı, iki işleç, **zıt sonuç.** Şimdi bunu bir izin kontrolüne koy:

```c
if (kullanici_yetkili & yonetici_modu) { ... }   /* & yazılmış */
```

`kullanici_yetkili = 1` (0001) ve `yonetici_modu = 2` (0010) ise sonuç **0** —
yani ikisi de doğru olduğu hâlde koşul yanlış çıkar. Ters durum da mümkündür:
farklı bayrakların ortak bir biti varsa, hiçbiri kastedilmediği hâlde koşul
doğru olur.

İkinci fark daha sinsi: **`&&` kısa devre yapar, `&` yapmaz.**

```c
if (p != NULL && p->deger > 0)   /* p NULL ise sağ taraf HİÇ çalışmaz */
if (p != NULL &  p->deger > 0)   /* p NULL olsa bile sağ taraf ÇALIŞIR → çökme */
```

Soldaki koruma, sağdakini korumak için yazılmıştı. `&` ile korumanın kendisi
devre dışı kalır.

## 2003: Çekirdekte Kayıp Bir Eşittir

Bu zayıflığın en bilinen gerçek vakası bir kaza değil, **bir girişim.**

Kasım 2003'te Linux çekirdeğinin CVS aynasına, kimsenin göndermediği iki satır
eklenmiş hâlde bulundu. `sys_wait4` içindeki koşul şuydu:

```c
if ((options == (__WCLONE|__WALL)) && (current->uid = 0))
```

Göze ilk bakışta bir kontrol gibi görünüyor. Ama sağdaki `=`, `==` değil —
karşılaştırma değil **atama.** O satıra giren bir süreç, kullanıcı kimliğini
sıfıra yazıyordu: yani `root`.

Üstelik atama ifadesinin değeri atanan değerdir — `0`, yani "yanlış". Koşul asla
doğru olmuyor, **ama yan etkisi çoktan gerçekleşmiş oluyordu.**

Girişim başarısız oldu: çekirdek asıl olarak BitKeeper'da tutuluyordu, CVS aynası
ondan türetiliyordu ve bu değişikliğin karşılığı asıl depoda yoktu. Tutarsızlık
otomatik kontrollerle fark edildi.

> 🔑 Buradaki ders savunma tarafında: kodu **kimin yazdığı** kadar, deponun
> kendisiyle tutarlı olup olmadığı da kontrol edilmeliydi — ve edildiği için
> yakalandı.

## Neden Derleyici Susar

Çünkü yazdığın şey **geçerli koddur.** `if (x = 5)` hatalı değil: x'e 5 atanır,
ifadenin değeri 5 olur, sıfırdan farklı olduğu için koşul doğru sayılır. Dilin
kuralları açısından her şey yolunda.

Derleyici sessiz kalmanın yanı sıra bir tuzak daha kurar: `&` ile `&&`'in
**işleç önceliği farklıdır.**

```c
if (a & b == c)     /* önce b == c hesaplanır, sonra a & (sonuç) */
if ((a & b) == c)   /* muhtemelen kastedilen buydu */
```

Parantez koymayı unutmak, üçüncü bir yanlış anlam üretir.

---

## Nasıl Önlenir

- **Uyarıları aç.** `-Wall` çoğu derleyicide `if (x = 5)` kalıbını
  *"suggest parentheses around assignment"* diye bildirir. Kasten atama yapıyorsan
  fazladan parantez koy — `if ((x = f()))` — hem derleyici susar hem okuyan anlar.
- **Koşullarda atamadan kaçın.** Ayrı satıra al: önce ata, sonra karşılaştır.
- **Yoda koşulu bir seçenek:** `if (5 == x)` yazarsan, yanlışlıkla `=` yazdığında
  derleme hatası alırsın (sabite atanamaz). Okunabilirliği tartışmalı, ama işe yarar.
- **Statik çözümleyici kullan.** `clang-tidy`, `cppcheck` gibi araçlar bu aileyi
  hedefleyen kurallar taşır; derleyicinin geçirdiklerini yakalarlar.
- **Bayrak kontrollerinde niyetini yaz.** Tek bir bayrağı sınıyorsan
  `if (bayraklar & YONETICI)` doğrudur; iki ayrı doğruluk değerini birleştiriyorsan
  `&&` doğrudur. Hangisini yaptığını cümleyle söyleyebiliyorsan işleç de belli olur.

## Özet — Aklında Tut

```
☐ & ve && ayrı işlemler, biri diğerinin kısaltması değil. | ve || için de aynı.
☐ & bit bit çalışır (12'de kurduğun devre), && "ikisi de doğru mu" der.
☐ a=1, b=2 için a&b = 0 ama a&&b = 1. Aynı sayılar, zıt sonuç.
☐ && kısa devre yapar, & yapmaz: NULL kontrolü & ile yazılırsa koruma çöker.
☐ = atama, == karşılaştırma. if (x = 5) geçerli koddur, derleyici susar.
☐ 2003'te Linux CVS aynasına (current->uid = 0) sokuldu; depo tutarsızlığından yakalandı.
☐ & ile == önceliği farklı: (a & b == c) beklediğin gibi gruplanmaz, parantez koy.
☐ Savunma: -Wall, koşulda atama yapma, statik çözümleyici, niyetini cümleyle söyle.
```
